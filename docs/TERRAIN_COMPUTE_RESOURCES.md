# Adaptive scientific computing

Open Settings → Computing Resources. Automatic policy uses backend host CPU affinity/cgroup quota, available and total RAM, and shows free storage. Manual mode persists memory fraction, task concurrency, tile size, per-operation cell caps, viewshed extent and ray budget alongside the active database. The effective limits are clamped to real available resources and engineering ceilings. Settings changes are rejected during admitted/queued calculations. A task records its effective snapshot in its result and terrain receipt.

Area statistics and DEM preparation use bounded source windows with exact halo semantics or streamed disk output. Advanced local derivatives use the existing tiled kernels where applicable. D8 and MFD traversal use chunked native JIT kernels. Large least-cost searches use an exact indexed Dijkstra frontier, with at most one entry per unsettled cell, and disk-backed search state. Hydrology, visibility, least-cost input elevations and encoded GeoTIFF outputs still require full grids; their budgets remain distinct and conservative. There is no silent resampling, approximation, or independent tile routing. A limit rejection is explicit.

Concurrent tasks reserve their per-task budgets before admission. Host memory pressure is checked cooperatively at bounded algorithm checkpoints; this is not a kernel-enforced memory limit. Interrupted streamed slope calculations retain atomic tile reductions, keyed by the source-file hashes, exact geometry, grid, gradient and tile size; repeating the identical calculation resumes committed tiles. Successful completion clears them; abandoned records expire after seven days. Other operations do not claim checkpoint/resume support. Existing optional OS job/cgroup protection for background workers is unchanged. Terrain API computation remains CPU-only; GPU acceleration and GPU memory budgets are not claimed. Multi-process scheduling, full out-of-core global hydrology/least-cost input and raster delivery, GPU execution, and generalized persistent jobs remain separate research engineering work. The scaling tests exercise a real >16-million-cell streamed DEM, >1-million-cell global flow routing, independent reference path costs and cancellation/resumption. These are synthetic acceptance fixtures, not universal hardware performance guarantees. Public DEM provider download quotas are independent of host settings. The scientific gate and full existing acceptance suites remain enabled.

## Execution and product delivery

Automatic or CPU-only backend selection uses actual CUDA device free/total memory if a CUDA-enabled native library is loaded. Horn and Zevenbergen-Thorne slope statistics on eligible in-memory grids can use the native GPU kernel with a bounded allocation; CPU fallback preserves availability. The CUDA CI compiles the physical-device test executable but cannot certify real GPU parity on a CPU runner. Run `ctest --test-dir build/cuda -R "^cuda_runtime$" --output-on-failure` on a CUDA workstation.

Optional OS-enforced memory mode spawns an isolated terrain task and joins a per-task Windows Job Object or an operator-provisioned Linux cgroup v2. Linux requires GEOFATHOM_WORKER_CGROUP and its actual memory.max must fit the task budget. Unsupported or failed enforcement is rejected explicitly; it never silently falls back. Default mode remains cooperative. Browser mesh streaming uses byte-bounded GPU tile buffers and the backend validates its actual tile working set.

Large API raster products are persisted as exact float32 GeoTIFFs, identified by SHA-256 and downloaded through the authenticated binary endpoint rather than base64 JSON. Small products preserve the old inline API. The browser caches the metadata and preview; binary download still requires browser Blob storage. Product storage has a separate explicit quota and user-controlled deletion. Global input grids and classification arrays still require RAM. Generalized external-memory flow propagation and resumable hydrology/mesh/export jobs remain out of scope of this implementation.

The dedicated scientific workflow additionally runs a 100,020,001-cell analytic GeoTIFF benchmark. It records elapsed seconds, sampled peak RSS, baseline RSS and checks the full native pixel population, complete halo population, analytic slope, mean height and tile count. The sampled RSS growth must not exceed 512 MiB on the acceptance runner. This is not a kernel peak-memory measurement; the hard-memory worker is a separate mechanism.
